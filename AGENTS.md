## Ветки и git

- Работаем **только в ветке `dev`**. Фича-ветки не создавать, в `main` напрямую не коммитить.
- Remote: `origin` = `https://github.com/petriashvili-dev/nodus-frontend.git`. Если remote не настроен — привязать его.
- **В начале сессии** подтянуть `main` в локальный `dev`:
  ```bash
  git checkout dev
  git fetch origin
  git merge origin/main
  ```
  Конфликты разрешить и показать пользователю; если слияние нетривиальное (несвязанная история, удаление чужих изменений) — сначала спросить.
- **После реализации фичи** — сборка, тесты, документация (см. ниже), затем отчёт пользователю. **Коммит и пуш в `origin dev` — только после явного подтверждения пользователя**:
  ```bash
  git add -A && git commit
  git push origin dev
  ```
- Одна фича — один коммит. Сообщение на английском: краткий заголовок в повелительном наклонении + список изменений.
- Репозиторий **публичный**. Секреты не коммитить никогда: API-ключи, токены, `.xcconfig` с ключами, `GoogleService-Info.plist` и т. п. Перед каждым коммитом проверить diff на ключи (`git diff --cached | grep -nE "sk-|key|secret|token"`). Клиент не ходит к LLM-провайдерам напрямую — только через backend.
- `build/`, `DerivedData/`, `xcuserdata/` — в `.gitignore`, не коммитить.

## Документация

Каждая новая фича или изменение поведения документируется **в том же коммите**, что и код:

- `docs/*.md` — на русском, описывают **как работает на клиенте**: экраны и потоки, состояния (pending/failed/conflict), какие эндпоинты вызываются, принятые решения, ссылки на файлы кода. Новая область → новый нумерованный файл и строка в `docs/README.md`.
- Новый компонент, токен, анимация, звук или паттерн текста → `DESIGN_SYSTEM.md`.
- Если для фичи не хватает чего-то в контракте backend или контракт расходится с поведением сервера — не обходить на клиенте, а сообщить пользователю (правка идёт в backend и `docs/ios/`).

## Сборка и тесты

- Проект: `nodus/nodus.xcodeproj`, схемы `nodus` и `NodusWidgetExtension`. iOS 18+, `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`.
- Проверка сборки:
  ```bash
  xcodebuild -project nodus/nodus.xcodeproj -scheme nodus -destination 'generic/platform=iOS Simulator' build
  ```
- Тесты — Swift Testing (`import Testing`, `#expect`/`#require`). Логику (Outbox, Sync, разбор ответов и ошибок, recurrence-проекции, планирование уведомлений, смена пояса) покрывать unit-тестами; сеть подменять через `URLProtocol`/протокол клиента, время — через инжектируемые часы, не `Date()` напрямую.
- Перед отчётом и коммитом: сборка без ошибок и новых предупреждений, тесты зелёные. Визуальные изменения проверить в симуляторе (в т. ч. Dynamic Type, Reduce Motion, VoiceOver на ключевых элементах). Не сообщать «готово», если что-то не собрано или не проверено — сказать прямо.

## Архитектурные правила

Целевая структура и порядок внедрения — §3 и §16 требований к iOS. Кратко:

- **Offline-first, optimistic UI.** Действие пользователя сразу меняет локальное состояние; сеть никогда не блокирует создание, правку, развязывание и перевязывание. Сервер — источник истины, клиент отправляет намерения.
- **Локальная мутация и запись Outbox — одна транзакция** локального хранилища. Хранилище — за протоколом `LocalStore` (сейчас SwiftData; GRDB — по решению из §2 требований).
- Разделять domain-модели, DTO backend и записи локальной БД. ViewModel не делает сетевых запросов и не трогает sync-курсор.
- Сеть, БД, sync и тяжёлые расчёты — вне main actor (actors). Main actor — только UI и короткие обновления состояния.
- SSE и push — только сигнал «сходи в sync»; данные — только из sync и ответов API.
- Экземпляры регулярных узлов считает сервер; клиент их не вычисляет (кроме ближайшего у офлайн-созданного узла).
- AI ничего не создаёт без подтверждения пользователя.
- Время: моменты в UTC, локальные дата/время + IANA-пояс отдельно; формат — по `docs/ios/README.md`.
- В логах нет пользовательского контента (тексты узлов, диктовка), токенов и кодов. Для поддержки логировать `X-Request-Id`.
- Токены — только Keychain. Строки UI — только через `Localizable.strings` (ru + en), не литералами.
- Код пишется в стиле окружающего: плотность комментариев, именование, идиомы. Новые экраны собираются из существующих компонентов `Components/` (см. `DESIGN_SYSTEM.md`).

### Критичные правила интеграции (от backend)

1. **Refresh токена — строго single-flight.** Одновременно не больше одного `POST /v1/auth/refresh`, остальные запросы ждут его результата. Повторное использование старого refresh-токена позже чем через 2 минуты сервер считает кражей и отзывает сессию; для анонимного аккаунта это **безвозвратная потеря доступа**. Новую пару записать в Keychain до использования. Подробно — `docs/ios/01-auth-and-account.md`.
2. **После бизнес-ошибки — только новый `Idempotency-Key`.** Сервер запоминает любой ответ, включая 4xx: повтор с тем же ключом вернёт ту же ошибку. Тот же ключ — только для сетевых сбоев, таймаутов, 5xx и повтора после refresh. Тело операции после постановки в очередь не менять. Таблица кодов — `docs/ios/02-outbox-and-errors.md`.
3. **Ленту брать из `GET /v1/feed`**, а не собирать из окна экземпляров. Окно для уведомлений покрывает 45 дней, а ближайшая годовщина может быть через полгода — в ленте сервер её покажет. Подробно — `docs/ios/04-feed-occurrences-notifications.md`.

## Скиллы

Проектные скиллы лежат в `.agents/skills/` (`.claude/skills` — симлинк на него); источники и коммиты — `.agents/skills-lock.json`.

| Скилл | Когда |
|---|---|
| `swiftui-expert-skill` | любой SwiftUI-код: состояние, композиция, производительность, актуальные API |
| `swiftui-design-skill` | новые экраны и ревью UI — **вместе с `DESIGN_SYSTEM.md`**, который имеет приоритет над общими советами скилла |
| `swift-concurrency` | actors, `Sendable`, MainActor-изоляция, async/await в Outbox/Sync/SSE |
| `swiftdata-pro` | работа с текущим SwiftData-хранилищем |
| `swift-testing-expert` | написание и ревью тестов |

Обновление скилла — заново скопировать из источника и обновить коммит в `skills-lock.json`.
