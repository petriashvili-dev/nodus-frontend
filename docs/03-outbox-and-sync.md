# Локальный кеш, Outbox и синхронизация

Требования — §4–§8 `03_Nodus_iOS_Requirements.md`. Контракт — `nodus_backend/docs/ios/02-outbox-and-errors.md`, `03-sync-engine.md`, `04-feed-occurrences-notifications.md`.

## Принцип

SwiftData — локальный кеш серверных данных плюс неподтверждённые изменения пользователя поверх него. Любое действие сразу меняет локальную запись и ставит намерение в Outbox **в одном `save`**; UI не ждёт сети. Сервер — источник истины: его ответы и Delta Sync перезаписывают кеш.

## Хранилище

`SyncEngine` зависит от протокола `LocalStore`, а SwiftData изолирована в `SwiftDataLocalStore`. Адаптер получает тот же сериализованный `ModelContext`, что и model actor синхронизации; операции `insert`/`delete` и изменение курсора фиксируются одним `save` на границах страницы sync или операции Outbox. Новые типы локальных записей подключаются через `LocalStoreRecord`. Тесты синхронизации продолжают использовать in-memory SwiftData контейнер через тот же адаптер.

| Модель | Что хранит |
|---|---|
| `ReminderNode` | узел в модели приложения + серверное: `serverVersion` (0 — сервер ещё не подтвердил), `timeZoneIdentifier`, `ownerId`, `memberCount`, `isUndated`, `syncIssueRaw` |
| `ReminderOccurrenceState` | локальное развязывание/перевязывание экземпляра, `key` — серверный ключ. Живёт, пока операция в пути; после ответа/sync удаляется |
| `ServerOccurrence` | готовые экземпляры сервера (`OccurrenceDto`), id `"{nodeId}:{key}"`; `isInFeed` — из последнего `GET /feed`, `isInHorizon` — окно уведомлений |
| `OutboxOperation` | намерение: метод, путь, тело, `idempotencyKey`, `entityId`, статус, попытки, `expectedVersion` |
| `SyncMetadata` | курсор, аккаунт кеша, отправленный пояс, флаг загрузки старых узлов |

Все поля добавлены со значениями по умолчанию — лёгкая миграция SwiftData сохраняет данные существующих установок.

## Действия → операции (`ReminderService`)

| Действие | Локально | Outbox |
|---|---|---|
| завязать | новый узел в поясе устройства | `POST /nodes` (id узла — клиентский) |
| изменить / перенести | поля узла | `PATCH /nodes/{id}` с полным шаблоном и `expected_version` |
| развязать | состояние экземпляра / статус одноразового | `PUT …/occurrences/{key}/untie { completed_at }` |
| вернуть в работу | то же | `PUT …/occurrences/{key}/retie` |
| удалить (после окна «Отменить») | удалить строку | `DELETE /nodes/{id}?expected_version=` |

- Ключ экземпляра — из `ServerOccurrence`; у узла, который сервер ещё не видел, — предсказуемый `g0-yyyyMMdd-0` (одноразовый — `once`).
- Несколько офлайн-правок схлопываются в одну неотправленную операцию; правки ещё не отправленного узла уходят в его `POST`. Удаление ещё не отправленного узла просто убирает его очередь.
- `expected_version` — версия, которую видел пользователь при правке. Ответ на собственную операцию продвигает её для следующих операций того же узла, поэтому цепочка своих правок не конфликтует сама с собой. Значение фиксируется при первой отправке, повторы шлют то же тело.

### Связь с моделью сервера (`NodeMapper`)

| Приложение | Сервер |
|---|---|
| без повтора | `one_time` (`date` + `time` в поясе узла) |
| по будням | `recurring` weekly пн–пт |
| каждые N дней / недель / месяцев | `recurring` daily / weekly (день недели старта) / monthly (число старта) |
| каждый год с исходной датой | `anniversary` (`date` = исходная, `track_years`) |
| каждые N лет | `recurring` yearly |

Обратно: правило → расписание, момент — старт правила (или ближайшая годовщина) в поясе узла. Несколько `times` в правиле приложение не редактирует — берётся первое.

## Отправка (`SyncEngine.flushOutbox`)

Операции одной сущности — строго по порядку; следующая ждёт, пока предыдущая не завершится. При старте `inFlight` возвращаются в `pending` и уходят с тем же ключом.

| Ответ | Что происходит |
|---|---|
| 2xx | ответ применяется как канонический, операция удаляется |
| сеть, таймаут, 5xx, `429 rate_limited`, `401` после refresh | `retryableFailure`, тот же ключ, backoff 1 с → 5 мин с jitter |
| `409 version_conflict`, личный узел | `current` применяется, правка пользователя уходит **новой** операцией с новым ключом и `expected_version = current.version` |
| `409 version_conflict`, совместный узел | `current` применяется, операция `blockedConflict`, на узле `syncIssueRaw = conflict` (выбор «моё / их» — с UI совместных узлов) |
| `409 node_already_exists` | создание уже было (потерянный ответ) — операция выполнена |
| `404` | локальное изменение откатывается, следующий pull восстанавливает правду |
| `403 feature_not_available` / `ai_consent_required` | `failed`, профиль перечитывается (`docs/01-ai-access.md`) |
| прочие 4xx | `failed` (сервер запомнил ответ за ключом), на узле `syncIssueRaw = rejected` |

## Получение (`SyncEngine.pull`, `refreshFeed`)

- Нет курсора → `GET /sync/snapshot`: серверные данные заменяются, узлы с неотправленными операциями не трогаются.
- Иначе `GET /sync?cursor&limit=500` до `has_more = false`; страница и `next_cursor` — одна транзакция. `410 cursor_expired` → snapshot.
- `node` upsert/delete, `occurrence_state`, `user` (→ профиль и доступ к AI); неизвестные типы пропускаются.
- Пока у узла есть незавершённая операция, его поля остаются локальными (overlay), обновляется только серверная версия.
- После pull: `GET /feed?from=вчера&to=+365` (что показывает нить) и `GET /occurrences?from=вчера&to=+45` (окно уведомлений).

## Цикл (`SyncCoordinator`)

Один цикл одновременно, триггеры во время цикла сливаются в один следующий:

1. аккаунт: при смене аккаунта (восстановление, потеря анонимной сессии) кеш сбрасывается, узлы устройства загружаются заново в новый аккаунт;
2. старые узлы (созданные до backend) ставятся в очередь создания один раз — с прежними id; выполненные одноразовые — плюс `untie`;
3. смена пояса устройства → `PUT /me/timezone` в очередь **после** уже ждущих правок;
4. Outbox → pull → лента.

Триггеры: запуск и foreground, локальное изменение (300 мс debounce), возвращение сети (`NWPathMonitor` — подсказка), `significantTimeChangeNotification` и `NSSystemTimeZoneDidChange`, таймер backoff, сигнал SSE. После цикла экран перечитывает хранилище и перепланирует уведомления.

## SSE (`EventStream`)

- `GET /v1/events` только в foreground (`ContentView` → `SyncCoordinator.enterForeground/enterBackground`), `Last-Event-ID` — текущий курсор.
- `sync.required` с `revision` больше курсора → запрос цикла; данные из события не применяются. После каждого (пере)подключения — цикл.
- Разрыв: переподключение 3 с → … → 60 с (или `retry:` сервера); `401` — refresh; `429 too_many_connections` — пауза не меньше 30 с.
- Разбор строк — `SSEParser` (`SSEParserTests`).

## Нить и уведомления (`TimelineService`)

- Узел, подтверждённый сервером, показывает ровно свои экземпляры из ленты (`isInFeed`) с историческими названиями; состояние — локальный overlay, если операция в пути, иначе серверное.
- Узел, созданный или изменённый офлайн, до подтверждения показывает ближайший экземпляр локального расчёта (`RepeatEngine`).
- Уведомления — из окна `isInHorizon` (ближайшие 12 экземпляров, лимит iOS — 64 запроса с учётом напоминаний заранее и повторов), для офлайн-узлов — из нити.

## Виджет

Виджет не открывает SwiftData: приложение пишет `widget-snapshot.json` в app group (`WidgetSnapshotWriter`, активные узлы сегодня и завтра), виджет только читает его. Раньше виджет держал копию схемы SwiftData — при её расхождении SwiftData мог мигрировать общее хранилище под урезанную схему.

## Только на устройстве

В контракте backend этого нет, поэтому остаётся локальным и не переносится между устройствами (вопрос к backend):

- пауза регулярного узла (`pausedUntil`);
- напоминания заранее (`leadTimes`) — настройка уведомлений этого устройства;
- скрытие отдельного экземпляра (`ReminderOccurrenceOverride`);
- «Отложить» из уведомления переносит узел (как «перенести»), а у регулярного — всю серию;
- узлы «когда-нибудь» без даты с других клиентов хранятся, но на нить не выводятся (нет редактора).
